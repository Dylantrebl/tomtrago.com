# Parallel Development Contract — Rails Upgrade (tomtrago.com)

**Purpose:** Run the Rails 5.1 → 7.2 upgrade using multiple agents (or multiple Cursor windows) safely. This contract prevents file conflicts, broken state, and merge surprises by defining **file ownership**, **strict sequence**, and **handoff rules**.

---

## How to use (one window per agent)

- **Window 1:** Open [docs/agents/01_UPGRADE_AGENT.md](agents/01_UPGRADE_AGENT.md) — run Upgrade agent only.
- **Window 2:** Open [docs/agents/02_CONFIG_AGENT.md](agents/02_CONFIG_AGENT.md) — run Config agent only (after Upgrade Stage 3).
- **Window 3:** Open [docs/agents/03_DEPLOY_AGENT.md](agents/03_DEPLOY_AGENT.md) — run Deploy agent only (after Config).
- **Window 4:** Open [docs/agents/04_QA_AGENT.md](agents/04_QA_AGENT.md) — run QA agent after each handoff (and after deploy).

**Index:** [docs/agents/README.md](agents/README.md)

Each window is self-contained. Do **not** let one agent edit files that another agent is editing at the same time.

---

## Execution order (mandatory)

Work is **sequential** for anything that touches repo files. Parallelism is allowed only where noted.

| Step | Agent | Allowed parallel? | Reason |
|------|--------|--------------------|--------|
| A | Upgrade (branch + baseline) | No | Creates branch; only one agent should create it. |
| B1 | Upgrade (Stage 1: Rails 5.2) | No | Only Upgrade touches Gemfile + runs bundle. |
| — | QA (local smoke) | After B1 commit | Yes — QA can run while no one edits; read-only. |
| B2 | Upgrade (Stage 2: Ruby 3.2, Rails 6.1) | No | Same as B1. |
| — | QA (local smoke) | After B2 commit | Yes. |
| B3 | Upgrade (Stage 3: Ruby 3.4, Rails 7.2) | No | Same. |
| — | QA (local smoke) | After B3 commit | Yes. |
| C | Config (production fixes) | No | Config is sole owner of production.rb, cable.yml in this step. |
| D | Deploy (Heroku) | No | Deploy runs push and Heroku CLI; no repo edits. |
| E | QA (production URL) | After D | Yes — QA only reads/browses. |

**Rule:** Only one agent may **edit** the following files at any time: `Gemfile`, `Gemfile.lock`, `config/**/*`, and any file under `app/` that the upgrade or config steps change. QA does **not** edit repo files.

## File ownership (who may edit what)

### Upgrade agent (exclusive during B1–B3)

| File / area | When |
|-------------|------|
| `Gemfile` | Stages 1–3 |
| `Gemfile.lock` | (generated by bundle) |
| `config/application.rb` | When `rails app:update` overwrites or conflicts |
| `config/boot.rb`, `config/environment.rb` | When `rails app:update` touches them |
| `config/routes.rb` | Only if merge from app:update |
| `config/environments/*.rb` | Only for non-production (e.g. development/test) if app:update changes them |
| New config files added by `rails app:update` | Accept or merge as per Upgrade checklist |

**Config agent must NOT edit** `Gemfile`, `Gemfile.lock`, or run `bundle` or `rails app:update`.

### Config agent (exclusive during C)

| File | When |
|------|------|
| `config/environments/production.rb` | Remove `read_encrypted_secrets`; set `config.assets.js_compressor = :terser` |
| `config/cable.yml` | Set production `url` to `ENV.fetch("REDIS_URL")` |

**Upgrade agent must NOT** edit production.rb or cable.yml during Stage 3 if Config will do it in phase C. Either Upgrade does it in B3 or Config does it in C — pick one and stick to it (this contract gives Config ownership in C so Upgrade stays focused on Gemfile/versions).

### Deploy agent

| Action | Ownership |
|--------|-----------|
| Heroku CLI commands | Deploy only |
| No repo file edits | — |

### QA agent

| Action | Ownership |
|--------|-----------|
| Browser (MCP or manual) | Read-only |
| Reading logs | Read-only |
| No edits to repo | QA must not change any file in the repo |

---

## DO NOT TOUCH (shared / lock rules)

- **While Upgrade is running** (any of B1–B3): No other agent may edit `Gemfile`, `Gemfile.lock`, or run `bundle` or `rails app:update`. No Config edits to `config/environments/production.rb` or `config/cable.yml`.
- **While Config is running** (C): No other agent may edit `config/environments/production.rb` or `config/cable.yml`. Upgrade must not run `app:update` or change Gemfile.
- **While Deploy is running** (D): No one should push another branch or run Heroku releases; Deploy owns the push and migrate.

---

## Handoff criteria (when to pass to the next agent)

| From | To | Handoff condition |
|------|-----|-------------------|
| Upgrade (each stage) | QA | Commit created; `bundle exec rails s` starts without error (Upgrade checks). |
| Upgrade (B3 done) | Config | Stage 3 committed; `zeitwerk:check` passes. |
| Config | Deploy | Config commit created; no uncommitted changes in `config/`. |
| Deploy | QA | Deploy completed; Heroku URL is known; logs show no boot error. |
| QA | (next or done) | QA documented pass/fail in their window; if fail, hand back to the owning agent (Upgrade/Config/Deploy). |

---

## Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Two agents edit `Gemfile` or `config/` at once | Strict sequence; one agent owns each phase; contract says "do not touch" during other agent's phase. |
| `bundle install` or server run while files change | Only Upgrade runs bundle and app:update; no Config or QA edits during B1–B3. |
| Merge conflicts when combining work | Work is on one branch (`upgrade-ruby-rails-heroku`); agents run in order, so no parallel commits on same files. |
| Production boot failure after deploy | Config agent is sole owner of production.rb and cable.yml; checklist includes secrets + Redis + assets. |
| QA reports pass but production breaks later | QA checklist includes production URL and asset/console checks; Deploy sets SECRET_KEY_BASE and REDIS_URL. |
| Forgetting to run a step | Each agent window has a checkbox-style checklist; contract lists mandatory order. |

---

## Branch and backup

- **Single branch for upgrade:** `upgrade-ruby-rails-heroku`
- **Backup:** Before starting, ensure `development` (or `main`) is pushed so you can revert: `git push origin development`
- **No parallel branches** for this upgrade: all agents commit to `upgrade-ruby-rails-heroku` in sequence.

---

## Summary

- One **window per agent**; one **checklist per window**.
- **Strict order:** Upgrade (A → B1 → B2 → B3) → Config (C) → Deploy (D) → QA (E).
- **File ownership:** Upgrade = Gemfile + app:update outputs; Config = production.rb + cable.yml in phase C; Deploy = Heroku only; QA = read-only.
- **Risks** are mitigated by no parallel edits on shared files and explicit handoff criteria.
